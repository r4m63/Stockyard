# ADR-007: Idempotency-keys retention — бессрочно вместе с ордерами

## Status

Proposed (2026-05-09)

## Context

[ADR-005](ADR-005-idempotency-key.md) ввёл `UNIQUE (user_id, idempotency_key)` в `orders`: повторный запрос с тем же ключом возвращает существующий ордер вместо создания нового. Открытым остался вопрос — **сколько хранить ключ**.

Варианты с точки зрения retention:

- **Слишком короткий TTL** (например, 24 ч с принудительным удалением) → клиент после длинной сетевой паузы / переустановки приложения ретраит, ключ уже почищен → создаётся дубль ордера → нарушение основного инварианта системы.
- **Слишком длинный TTL** (полгода и более) → требуется cleanup-job (cron-DELETE или partition-drop), добавляется операционная сложность и риск задеть другие колонки `orders`.
- **Внешнее хранилище** (Redis с TTL, отдельная таблица `idempotency_keys`) → новые failure modes (Redis потерял dump.rdb после рестарта → ретрай создаёт дубль) и дополнительная сущность для сопровождения.

Объёмы (см. [06-data §6.6](../06-data.md#66-объёмы-хранилищ)): `orders` за год — ~3.6 М × 300 B = 1 GB; колонка `idempotency_key` (≤ 36 байт UUID/ULID) добавляет ~130 МБ/год. Это пренебрежимо относительно общего объёма.

## Decision

Idempotency-key хранится **бессрочно** в колонке `orders.idempotency_key`. Никаких TTL, никакого cleanup, никакого внешнего хранилища.

Срок жизни ключа на стороне клиента — рекомендуемые 24 часа после действия пользователя (фиксируется в API-документации). Это влияет только на клиента: после 24 ч клиент сам генерирует новый ключ для нового действия.

## Consequences

**Положительные:**

- Ноль операционной сложности: нет cron-job, нет таблицы `idempotency_keys`, нет TTL-подсистемы.
- Защита от ретраев работает всегда — независимо от того, ретраит ли клиент через минуту, час или неделю; ключ найдётся в `orders`.
- Storage-overhead — ~130 МБ/год при 3.6 М ордеров. На годовом масштабе MVP — пренебрежимо.
- Ключ остаётся доступным для трейсинга/корреляции в логах через `stockyard.idempotency_key` атрибут (см. [09-observability §9.12](../09-observability.md#912-storage-instrumentation)).

**Отрицательные:**

- При отдалённом росте до 100 М+ ордеров колонка раздувает индекс `UNIQUE (user_id, idempotency_key)`. Точка эволюции — добавить partition pruning (см. [ADR-008](ADR-008-pg-no-partitioning-mvp.md), точка эволюции) или вынести ключ в отдельную таблицу с retention.
- Любая утечка БД раскрывает идемпотентность ключи всех когда-либо существовавших ордеров. На уровне MVP это дополнительный аргумент в пользу шифрования бэкапов на отдыхе (📦 backlog).

**Нейтральные:**

- Согласовано с ADR-005 — не противоречит, конкретизирует.

## Alternatives considered

- **TTL 48 часов с `DELETE FROM orders WHERE created_at < now() - interval '48 hours' AND status = 'REJECTED'`.** Отвергнуто: REJECTED-ордера — часть audit trail, удалять нельзя. И даже если удалять только REJECTED, остаётся проблема EXECUTED-ордеров — их хранить вечно надо.
- **Отдельная таблица `idempotency_keys (key TEXT PK, response_body BYTEA, expires_at TIMESTAMPTZ)` с TTL 48 ч.** Отвергнуто: всё, что нужно для повторного ответа клиенту, уже есть в `orders` (id, status, executed_at, price_cents). Лишняя сущность без бизнес-выигрыша.
- **Redis с TTL 48 часов.** Отвергнуто как **опасно**. Redis в нашей конфигурации не persistent (RDB hourly snapshot, AOF off — см. [12-storage-operations §12.2.2](../12-storage-operations.md#1222-redisconf)). При рестарте часть ключей теряется → ретрай → дубль ордера → нарушение основного финансового инварианта. Опасность повторного списания денег не оправдывает экономии 130 МБ/год в PG.
- **Партиционирование `orders` по месяцам с автоматическим detach старых партиций.** Отдалённая точка эволюции, не для MVP — см. ADR-008.

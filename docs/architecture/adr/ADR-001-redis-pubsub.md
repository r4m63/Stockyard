# ADR-001: Redis Pub/Sub как брокер котировок

## Status
**Accepted** (2026-05-09)

## Context

Системе нужен **брокер сообщений** для распространения потока котировок: Quotes Service генерирует ~50 тиков/сек, которые должны fan-out-иться в API Gateway и далее по 10 000 WebSocket-соединениям.

Требования:
- Низкая latency (< 100 мс от публикации до клиента).
- Fanout «один публикатор — много подписчиков».
- Ordering внутри одного тикера желателен, но не критичен.
- Потеря отдельных тиков допустима (следующий придёт через ~1 сек).
- Минимум новых компонентов в инфраструктуре.

Из ТЗ §4: брокер сообщений — **Redis Server / KeyDB**. Это формальное ограничение.

## Decision

Используем **Redis Pub/Sub** (`PUBLISH` / `SUBSCRIBE`) как основной транспорт котировок между Quotes Service и API Gateway.

Дополнительно дублируем поток в **Redis Streams** (`XADD stream:quotes`) как durable backup на случай, если в будущем понадобится догонять пропущенное.

## Consequences

**Положительные:**
- Уже имеющийся компонент инфраструктуры — нулевая стоимость интеграции.
- Sub-millisecond latency на одной машине, миллисекунды по сети.
- Простой API, легко отлаживать (`redis-cli MONITOR`).
- Соответствует ТЗ.

**Отрицательные:**
- **At-most-once доставка** — если ни один Gateway не подписан в момент `PUBLISH`, тик потерян.
- Нет встроенной репликации сообщений — Pub/Sub не персистентен.
- Pattern subscribe (`SUBSCRIBE channel:quotes:*`) медленнее обычного на больших количествах каналов.

**Нейтральные:**
- Дублирование в Streams даёт durability, но удваивает память Redis (~2 МБ при maxlen 100k — пренебрежимо).
- Нагрузка на Redis (50 PUBLISH/sec × несколько подписчиков) — в тысячи раз ниже потолка.

## Alternatives considered

- **Apache Kafka** — индустриальный стандарт для streaming, но:
  - Не входит в стек ТЗ.
  - Требует ZooKeeper/KRaft, отдельной операционной нагрузки.
  - Overkill для 50 событий/сек.
  - Избыточно для учебного MVP.
- **NATS** — лёгкий и быстрый, но:
  - Не входит в стек ТЗ.
  - Ещё один компонент инфраструктуры.
- **PostgreSQL LISTEN/NOTIFY** — встроено в PG, но:
  - Не масштабируется на 50к msg/sec.
  - Нагружает primary БД, которую и так бережём.
- **gRPC streaming напрямую от Quotes Service в Gateway** — но:
  - Нужно решать обнаружение сервисов и реконнекты вручную.
  - Не fanout: каждый Gateway держит N×M streams.

# ADR-005: Идемпотентность ордеров через UNIQUE-индекс

## Status
**Accepted** (2026-05-09)

## Context

Мобильный клиент может ретраить запрос на размещение ордера из-за плохой сети, таймаута или двойного клика пользователя. **Без защиты от повторов одно действие пользователя может привести к нескольким ордерам и двойному списанию денег.**

Нужен механизм, гарантирующий: «один логический ордер — одна запись в БД, один ответ клиенту, независимо от количества HTTP-повторов».

## Decision

1. Клиент генерирует **`Idempotency-Key`** (UUID/ULID) на каждое уникальное действие пользователя и шлёт его в HTTP-заголовке.
2. В таблице `orders` есть **UNIQUE-индекс по `(user_id, idempotency_key)`**.
3. При попытке INSERT с уже существующим ключом ловим `unique_violation`, читаем существующий ордер и возвращаем тот же ответ.
4. Срок жизни ключа на стороне клиента — **24 часа**; в БД — постоянный (вместе с ордером).

```sql
CREATE TABLE orders (
    ...
    idempotency_key TEXT,
    UNIQUE (user_id, idempotency_key)
);
```

## Consequences

**Положительные:**
- Атомарность гарантируется самой БД через индекс — нет окон гонки.
- Не требует distributed lock или координации между репликами Core Service.
- Простой контракт с клиентом: один заголовок.
- Защищает и от двойного клика, и от ретраев на сетевых ошибках.

**Отрицательные:**
- Клиент обязан корректно генерировать ключи (один ключ на одно действие). При баге на клиенте — два разных ордера с разными ключами, защита не сработает.
- Хранение ключа постоянно в `orders` — небольшой оверхед на запись (~36 байт), пренебрежимо.

**Нейтральные:**
- Ключ можно использовать для трейсинга/корреляции в логах.

## Alternatives considered

- **Distributed lock в Redis (`SET lock:order:{userId} NX EX 5`)**:
  - Защищает только от concurrent-запросов в окне TTL.
  - Не помогает, если повтор пришёл через минуту (например, после сетевой паузы).
  - Не нужен при наличии UNIQUE-индекса.
  - Помечен в [06. Архитектура данных](../06-data.md) как «избыточно для MVP».
- **Хранение ключей в отдельной таблице `idempotency`**:
  - Лишний JOIN и лишняя запись.
  - Без выигрыша по сравнению с индексом в `orders`.
- **Серверная генерация ключа**:
  - Не защищает от повторов (каждый ретрай получит новый ключ).
  - Идемпотентность по определению требует, чтобы ключ был **снаружи** транзакции.
- **Принимать дубль и компенсировать постфактум**:
  - Сложнее, опаснее (что если компенсация тоже сфейлит?), хуже UX.

# ADR-004: Единственный транзакционный writer — DB Service

## Status
**Accepted** (2026-05-09)

## Context

Финансовые операции системы (создание ордера, изменение баланса, изменение позиции, запись в audit-лог) должны быть **строго ACID**: либо все четыре изменения произошли, либо ни одно. Это критично для корректности денежных расчётов.

Возникает архитектурный выбор: где живёт эта транзакционность.

## Decision

Все мутации финансово-значимых данных проходят **только через DB Service**, в **одной транзакции PostgreSQL** на действие. API Gateway, Quotes Service и любой другой компонент **никогда не пишут** напрямую в `accounts`, `orders`, `positions`, `transactions`.

DB Service — **единственный legitimate writer** этих таблиц.

Никаких распределённых транзакций (XA, 2PC) и никаких саг **в MVP** не вводим.

## Consequences

**Положительные:**
- Все инварианты проверяются и поддерживаются в одной БД, в одной TX — это самый простой и надёжный режим.
- ROLLBACK гарантирует консистентность при любой ошибке внутри TX.
- Простая ментальная модель: «если хочешь поменять деньги — иди в DB Service».
- Легко тестировать: интеграционные тесты с Testcontainers против реальной PG.

**Отрицательные:**
- DB Service — потенциальный bottleneck. На 10к CCU это не страшно (~170 TPS из 3–5к, см. [08. Масштабирование](../08-scaling.md)), но при 10× росте упрёмся.
- При недоступности DB Service вся торговая часть лежит — нет graceful degradation.

**Нейтральные:**
- Чтение цены из Redis происходит **до** старта транзакции (вне TX), чтобы не держать TX долгой во время сетевого вызова.

## Alternatives considered

- **Распределённые транзакции (2PC через PostgreSQL XA + Redis)**:
  - 2PC хрупок при отказах координатора.
  - Redis не поддерживает полноценный XA.
  - Усложняет код многократно ради сценария, который у нас не возникает (все изменения в одной БД).
- **Saga pattern (последовательные локальные TX с компенсациями)**:
  - Полезно при scale > 5к ордеров/сек или при действительно распределённом state.
  - У нас один writer и одна БД — saga излишне.
  - Помечен в [07. Согласованность §7.8](../07-consistency.md) как «возможное будущее».
- **Event Sourcing с CQRS**:
  - Огромная переусложнённость для учебного MVP.
  - Команда из студентов утонет в инфраструктуре.
- **Запись напрямую в PG из Gateway**:
  - Нарушит изоляцию слоёв.
  - Потребует знания SQL и схемы в нескольких сервисах.
  - Усложнит тестирование и эволюцию схемы.

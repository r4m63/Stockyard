# ADR-003: REST + WebSocket между мобилкой и Gateway

## Status
**Accepted** (2026-05-09)

## Context

Нужно выбрать **протокол внешнего API** между мобильными клиентами (Android Compose, React Native) и API Gateway.

Требования:
- Двусторонняя коммуникация: клиент шлёт ордера, сервер пушит котировки.
- Простота отладки (curl, Postman).
- Поддержка из мобильных платформ без экзотических библиотек.
- Прохождение через корпоративные прокси и мобильные сети.
- Лёгкое логирование и трейсинг.

## Decision

Используем **гибрид**:
- **HTTPS REST + JSON** для всех request/response операций (аутентификация, ордера, портфель, история, каталог).
- **WebSocket Secure (WSS)** + **JSON-кадры** только для потока котировок и пуша уведомлений об исполнении ордеров.

Внутренний API между Gateway и DB Service — также **HTTP/1.1 + JSON** (по тому же принципу симметрии).

## Consequences

**Положительные:**
- Каждый запрос можно отправить через `curl` и проверить вручную.
- Стандартные инструменты на всех платформах: `OkHttp` (Android), `fetch`/`axios` (RN), `requests` (Python для Simulator).
- WS поддерживается браузерами и нативными мобильными SDK без proto-кодогенерации.
- Простая интеграция с OpenAPI спецификацией и Swagger UI.
- Кеширование REST GET через стандартные HTTP-механизмы (ETag, Cache-Control).

**Отрицательные:**
- JSON многословен → больше байт на проводе.
- Нет нативной типизации контрактов (нужны OpenAPI или ручная синхронизация).
- Polling-патерны легко делать «на коленке», что приведёт к лишней нагрузке (страховка — rate limit на Gateway).

**Нейтральные:**
- HTTP/2 даёт мультиплексирование, нивелируя часть оверхеда (включается на nginx).

## Alternatives considered

- **gRPC**:
  - Лучше типизация и меньше bytes-on-wire.
  - Хуже поддержка в браузерах (нужен gRPC-Web прокси).
  - Сложнее отлаживать без специальных инструментов.
  - Кодогенерация добавляет шаг сборки.
  - Команде из 10 студентов — лишний барьер входа.
- **GraphQL**:
  - Отличен для сложных UI с разнородными запросами; у нас простой набор эндпоинтов.
  - Subscription-механизм избыточен — у нас один pub-канал с тиками.
- **Server-Sent Events (SSE)** для котировок:
  - Только server → client, не двусторонний.
  - Хуже поддержка из RN и нативных мобильных SDK.
- **MQTT**:
  - Хорош для IoT, но требует отдельный брокер и не приживается на мобильных HTTP-стеках.
